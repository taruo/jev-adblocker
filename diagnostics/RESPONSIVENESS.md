# Chrome 応答性の原因調査と修正

調査開始: 2026-09-23 01:06:18.223 +09:00（依頼時刻）

原因調査の対象: commit `31039ef` / 拡張 `0.3.1`。
原因を対照実験で確認した後、`0.3.2` で下記の修正と実DOM回帰確認を実施した。

## 再現できた主因

旧版 `content.js` の `unhide()` は、非表示用クラスが存在しなくても毎回
`element.classList.remove("jev-adblocker-hidden")` を実行する。
既存の class 属性がある要素では、値が同じでも属性の変更通知が発生する。
`MutationObserver` がそれを受けて判定済みスコアを適用し、低スコアなら
再び `unhide()` を実行する。この循環がブラウザの microtask を占有する。

```text
低スコアの結果
  → applyScore() → unhide() → classList.remove()
  → MutationObserver → reapplyCachedScores()
  → applyScore() → unhide() → …
```

旧版の該当箇所: `content.js:144`（削除）、`:151`（スコア適用）、`:483`（再適用）、
`:501`（監視コールバック）。候補が広告である必要はなく、通常コンテンツを
広告ではないと正しく判定した場合にも発生する。

## ブラウザでの対照実験

ローカルの静的 fixture 上で旧版の `content.js` をそのままロードした。
DOM と MutationObserver は実際の Chromium 152 の実装を使用した。
Chrome 拡張メッセージだけを置き換え、TypeSafe API は呼ばず、設定とスコアを
固定応答した。候補は class="sidebar" を持つ aside 要素1個。

監視が200回に達したらテスト側で必ず切断する。無制限には実行しない。

| 条件 | 監視コールバック | 寸法読取 | API相当の要求 | 強制停止前にタイマー実行 |
|---|---:|---:|---:|---|
| 0.3.1、低スコア 0.10 | 200（上限到達） | 206 | 1 | できなかった |
| 0.3.1、高スコア 0.95 | 1 | 8 | 1 | できた |
| 削除を存在時だけにした比較用コード、低スコア 0.10 | 0 | 7 | 1 | できた |

低スコアの200回は14.2 msで発生した。これは再発火回数の測定であり、
実サイトのCPU使用率や停止時間を推定するためのベンチマークではない。
比較用コードは診断サーバーが返すメモリ上のコピーだけを変更し、
リポジトリの `content.js` や読み込み済み拡張には適用していない。

初回調査の生の結果はローカルの `observer-repro-results.jsonl` に保存した。
JSONLはGit対象外とし、回帰テストを実行すると新しい結果が自動保存される。

## 前回の制限で止まらない理由

- 1.5秒間隔は `scheduleScan()` のタイマーにしか適用されない。
  監視コールバック内の再適用はタイマーより前に同期実行される。
- API同時実行2件の制限はService Workerの通信処理だけに適用される。
  再現はAPI相当の要求1回だけで発生している。
- 自分のマーカーを除外する条件は再適用の後にある。
  また data 属性の除外条件は、そもそもその属性が監視フィルターにないため
  class 属性の自己発火を防げない。
- 以前の単体テストは MutationObserver を空のモックに置き換えていた。
  通知→DOM書換え→再通知というブラウザの挙動を検証できていなかった。

## 副次的な問題と対応（実サイトでの負荷量は未測定）

- `querySelectorAll()` の実行後に300件で打ち切っているため、検索範囲・検索時間は
  制限されない。body/htmlの属性変更でも大きな範囲が再検索され得る。この制約は残る。
- backlog が300件でもルート自身は上限確認なしで追加される。
  64ルートを使った静的プローブでは364件に増加し、検索も64回実行された。
  0.3.2ではルート追加前にも上限を確認し、満杯なら検索を行わない。
- 旧版の `fingerprint()` は監視ループのたびに寸法と配下の全文を読み取っていた。
  0.3.2では監視コールバックから呼ばない。ただし全文取得後に切り詰める処理は残る。
- サイト別OFF/キー未設定でも旧版は監視が続いていた。0.3.2では切断する。

## 0.3.2での修正

- クラス・data属性の変更を必要な場合だけ行い、同じ値への書込みを止めた。
- 自前class変更の通知をその通知バッチで消費する。将来サイトが同じclass値へ戻した変更は無視しない。
- 監視コールバックは予約だけにし、表示変更・寸法読取・検索はタイマーへ遅延した。
- 保存済みスコアの再適用をAPI待機・再試行停止から分離し、401後でもしきい値変更を反映する。
- OFF・キー未設定では監視と走査・再適用タイマーを停止し、ON時には停止中の追加要素も再走査する。
- 設定変更前の古い成功・失敗応答を無視し、新しい設定で処理を再開する。
- サイトがクラスを書き換えてもdata属性で非表示状態を追跡し、件数の二重加算を防ぐ。

## 修正版の回帰確認

Chromium 152 の実DOMで、履歴版の対照1ケースと修正版14ケースを実行し、15/15成功。
通常タスクが実行されること、ループの安全上限に達しないこと、監視コールバック内で
寸法読取を行わないことも確認した（意図的に停止させる旧版対照を除く）。

| ケース | 監視コールバック | 判定要求 | 結果 |
|---|---:|---:|---|
| 旧版・低スコア（対照） | 200 | 1 | 循環を再現し安全停止 |
| 修正版・低スコア | 0 | 1 | 表示維持、タスク実行可 |
| 高スコア | 1 | 1 | 非表示 |
| 不明スコア | 0 | 1 | 表示維持 |
| 低スコア後のclass変更 | 1 | 2 | 再判定して表示維持 |
| サイトによるマーカー削除 | 3 | 1 | キャッシュから復元、件数1 |
| 以前のclass値への再変更 | 4 | 4 | 変更を取りこぼさず再判定 |
| 同じ要素の内容置換 | 2 | 2 | 古い非表示を解除 |
| OFF→ON・停止中の要素追加 | 3 | 2 | 停止中の監視0、復帰後に追加要素も判定 |
| キー削除→再設定 | 3 | 2 | 停止・表示復元・再開 |
| しきい値変更 | 3 | 1 | API再呼出しなしで表示更新 |
| 認証エラー後のしきい値変更 | 4 | 2 | 通信を再試行せず表示更新 |
| 古い成功応答 | 0 | 2 | 古い結果を捨て新世代で再開 |
| 古い失敗応答 | 0 | 2 | 古いエラーを捨て新世代で再開 |
| キー未設定で開始 | 0 | 0 | 監視・判定とも停止 |

修正版の監視コールバック内の寸法読取は全ケース0回。
結果ログは `observer-regression-results.jsonl` に自動保存する。

ユーザーの既存Chromeプロファイルで個々のタブとの対応付けや拡張ON/OFFの
比較はしていないため、ほかのサイト・拡張の負荷が併存するかは未確定。
実サイト全体の負荷が完全に解消したという主張ではなく、旧版単体の応答不能経路を
再現し、修正版でその経路が切れたことを確認したもの。

## 再現手順（開発用のみ）

1. Git履歴の `31039ef` を含むプロジェクト直下で `node diagnostics/serve-observer-repro.cjs` を実行。
2. 拡張を入れていない隔離ブラウザで `http://127.0.0.1:8765` を開く。
3. `PASS (15/15)` の完了表示と自動保存されたJSONLを確認し、Ctrl+Cでサーバーを終了。

サーバーは127.0.0.1だけで待ち受ける。旧版ソースはGitから読み取り、修正版は
現在の `content.js` を加工せず配信する。インストール済み拡張には操作を行わない。

この診断用Node.jsは拡張の実行要件ではない。APIキー・npm依存は不要。

仕様上の根拠: [DOMTokenList.remove](https://dom.spec.whatwg.org/#dom-domtokenlist-remove)、
[属性の変更通知](https://dom.spec.whatwg.org/#concept-element-attributes-change)。
